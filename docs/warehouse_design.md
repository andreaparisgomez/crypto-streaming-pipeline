# Warehouse Design

## Overview

As the project evolved from a real-time cryptocurrency streaming pipeline into a broader analytics platform, a dedicated warehouse layer was introduced to support historical analysis, dimensional modelling, dashboard reporting, and analytical querying.

The original PostgreSQL database (`crypto_db`) functions primarily as an operational datastore for streaming ingestion and near real-time persistence. While this structure works well for transactional inserts and stream consumption, it is not optimised for analytical workloads or BI reporting.

To address this, a separate cloud-based PostgreSQL warehouse was implemented using Neon.

The warehouse layer enables:

- historical trend analysis
- dimensional modelling
- aggregated analytical queries
- dashboard optimisation
- separation of operational and analytical workloads
- scalable reporting architecture

The resulting architecture now resembles a simplified modern data platform with distinct ingestion, processing, warehousing, orchestration, and visualisation layers.

---

## Architectural Separation: OLTP vs OLAP

### Operational Layer (OLTP)

The operational PostgreSQL database (`crypto_db`) is designed for transactional and streaming workloads. Its primary purpose is to support high-frequency ingestion, intermediate persistence, and real-time processing across the streaming pipeline.

This layer stores data produced directly by Kafka consumers and Spark Structured Streaming jobs before analytical transformation and warehousing.

Characteristics of the operational layer include:

- continuous inserts and updates
- append-heavy workloads
- near real-time persistence
- denormalised streaming records
- optimisation for ingestion speed rather than analytical querying

The operational database acts as the intermediate persistence layer between streaming infrastructure and downstream analytical processing.

Examples of operational tables include:

- `crypto_metrics`
- `historical_crypto_prices`
- `youtube_sentiment_metrics`
- `daily_youtube_sentiment_summary`

This layer is not intended for dashboard consumption or complex historical analysis.


### Analytical Warehouse Layer (OLAP)

The analytical warehouse layer is implemented using Neon PostgreSQL (`neondb`) and is designed specifically for analytical querying, dimensional modelling, and dashboard reporting.

Unlike the operational database, the warehouse is optimised for read-heavy workloads and historical analysis rather than continuous transactional ingestion.

This separation enables cleaner architecture, improved reporting performance, and better scalability for BI workloads.

The warehouse layer stores transformed and aggregated data using a simplified star schema design composed of fact and dimension tables.

Characteristics of the warehouse layer include:

- historical analytical storage
- dimensional modelling
- aggregated metrics
- optimised read/query performance
- dashboard-friendly schema design
- separation of operational and analytical concerns

Examples of warehouse tables include:

- `fact_crypto_price_daily`
- `fact_youtube_sentiment_daily`
- `dim_date`
- `dim_channel`
- `dim_source`
- `dim_sentiment_label`

The warehouse serves as the primary data source for Looker Studio dashboards and analytical reporting.

By separating the operational streaming layer from the analytical warehouse layer, the platform more closely reflects real-world modern data architectures used in production analytics systems.

## Warehouse Architecture

The warehouse follows a simplified star schema design composed of fact and dimension tables.

This modelling approach was chosen to improve analytical query performance, simplify dashboard development, and separate measurable business events from descriptive contextual data.

The warehouse structure is intentionally designed for BI consumption and historical analysis rather than transactional processing.


### Fact Tables

Fact tables store measurable business metrics and analytical events generated by the streaming pipelines.

These tables contain the quantitative metrics consumed by dashboards and analytical queries.

#### fact_crypto_price_daily

Stores historical cryptocurrency market metrics aggregated by date and asset.

Metrics include:

- average price
- minimum price
- maximum price
- market capitalisation
- trading volume

Foreign keys:

- `date_id`

This table powers the market analytics dashboard layer.


#### fact_youtube_sentiment_daily

Stores aggregated YouTube sentiment metrics grouped by publication date, source query, channel, and sentiment label.

Metrics include:

- comment count
- average sentiment score
- weighted sentiment score
- engagement score

Foreign keys:

- `date_id`
- `source_id`
- `channel_id`
- `sentiment_id`

This table powers the sentiment analytics and correlation dashboard layers.


### Dimension Tables

Dimension tables provide descriptive business context for analytical queries.

Separating dimensions from facts reduces duplication, improves consistency, and simplifies reporting logic.


#### dim_date

Provides reusable calendar attributes for time-series analysis.

Attributes include:

- full date
- year
- month
- quarter
- weekday

This dimension simplifies dashboard filtering and historical aggregation.


#### dim_source

Stores the original YouTube search query or topic context used during ingestion.

Examples include:

- Bitcoin
- Ethereum
- Solana

This enables sentiment analysis by topic or search source.


#### dim_channel

Stores YouTube channel metadata.

This dimension enables channel-level engagement and sentiment analysis.


#### dim_sentiment_label

Stores sentiment classification categories.

Examples include:

- positive
- neutral
- negative

This normalisation improves consistency across analytical queries and dashboards.


### Warehouse Design Rationale

A dimensional warehouse design was chosen for several reasons:

- simplify BI dashboard development
- improve analytical query readability
- separate metrics from descriptive metadata
- reduce duplication across analytical tables
- support scalable historical analysis
- align with common modern analytics engineering practices

The resulting structure allows dashboards and analytical queries to operate against stable, business-oriented data models rather than raw streaming outputs.

## Data Flow

The platform consists of two primary streaming pipelines:

1. Cryptocurrency market data pipeline
2. Social sentiment analytics pipeline

Both pipelines follow a similar architectural pattern:

```text
API ingestion
    ↓
Kafka streaming
    ↓
Spark processing
    ↓
Operational PostgreSQL storage
    ↓
Airflow orchestration
    ↓
Neon analytical warehouse
    ↓
Looker Studio dashboards
```

This layered architecture separates ingestion, processing, warehousing, and visualisation concerns.


### Cryptocurrency Market Pipeline

The cryptocurrency pipeline ingests live market data from the CoinGecko API.

#### Flow Overview

```text
CoinGecko API
    ↓
Kafka Producer
    ↓
Kafka Topic: crypto_prices
    ↓
PySpark Structured Streaming
    ↓
Kafka Topic: crypto_metrics
    ↓
PostgreSQL Operational Database
    ↓
Airflow Warehouse Loading DAGs
    ↓
Neon Warehouse
    ↓
Looker Studio Dashboard
```

#### Pipeline Responsibilities

##### Kafka Producer

The producer continuously ingests live cryptocurrency market data including:

- current price
- market capitalisation
- trading volume
- daily price changes

The producer publishes records to the `crypto_prices` Kafka topic.


##### Spark Structured Streaming

Spark consumes records from Kafka and performs:

- schema parsing
- stream transformations
- metric extraction
- rolling aggregations

Processed records are then published to the `crypto_metrics` Kafka topic.


##### PostgreSQL Operational Layer

A PostgreSQL consumer persists processed streaming metrics into the operational database (`crypto_db`).

This layer acts as intermediate persistence between streaming infrastructure and downstream analytical processing.


##### Airflow Warehouse DAGs

Airflow orchestrates:

- historical backfill loading
- date dimension loading
- warehouse fact table population
- daily aggregation workflows

The resulting transformed data is loaded into the Neon analytical warehouse.


### YouTube Sentiment Pipeline

The sentiment pipeline ingests YouTube comments related to cryptocurrency topics and performs sentiment analysis using Spark processing.

#### Flow Overview

```text
YouTube API
    ↓
YouTube Producer
    ↓
Kafka Topic: youtube_raw_comments
    ↓
PySpark Sentiment Processor
    ↓
Kafka Topic: youtube_sentiment_metrics
    ↓
PostgreSQL Operational Database
    ↓
Airflow Sentiment Aggregation DAGs
    ↓
Neon Warehouse
    ↓
Looker Studio Dashboard
```


#### Pipeline Responsibilities

##### YouTube Producer

The producer retrieves YouTube comments associated with cryptocurrency-related search queries.

Examples include:

- Bitcoin
- Ethereum
- Solana

Metadata collected includes:

- comment text
- channel information
- engagement metrics
- publication timestamps

Raw records are published to the `youtube_raw_comments` Kafka topic.


##### Spark Sentiment Processing

Spark Structured Streaming performs:

- sentiment scoring
- weighted sentiment calculations
- engagement scoring
- metadata transformation

Processed sentiment records are published to the `youtube_sentiment_metrics` Kafka topic.


##### Event Time vs Processing Time

A key design consideration emerged during development regarding time-series aggregation.

Initially, sentiment metrics were aggregated using processing timestamps (`processed_at`), which incorrectly concentrated all sentiment activity into the day the pipeline was executed.

This was later corrected by aggregating sentiment using the original YouTube comment publication timestamp (`published_at`).

This distinction between:

- event time
- processing time

is an important streaming systems concept and enabled meaningful historical alignment between cryptocurrency prices and social sentiment.


### Warehouse Consumption Layer

The Neon warehouse acts as the central analytical layer for dashboard reporting.

Looker Studio connects directly to warehouse views rather than raw operational tables.

This separation provides:

- cleaner analytical models
- improved dashboard performance
- simplified BI querying
- reduced coupling between ingestion and reporting systems

Dashboard views include:

- `vw_crypto_price_daily`
- `vw_youtube_sentiment_daily`
- `vw_daily_sentiment_summary`

These views expose dashboard-friendly structures optimised for visualisation and analytical reporting.

## Airflow Warehouse Loading

Apache Airflow is used as the orchestration layer for scheduled transformations, warehouse loading, aggregation workflows, and operational monitoring.

While Kafka and Spark manage real-time streaming and processing, Airflow is responsible for coordinating analytical workflows and warehouse population on a scheduled basis.

This separation reflects a common modern data architecture pattern:

- streaming systems handle ingestion and transformation
- orchestration systems manage scheduled analytical workflows


### Airflow Responsibilities

The Airflow layer is responsible for:

- loading warehouse dimension tables
- populating warehouse fact tables
- aggregating daily sentiment summaries
- validating warehouse data
- monitoring pipeline health
- orchestrating analytical refresh workflows

Airflow therefore acts as the bridge between operational streaming infrastructure and the analytical warehouse layer.


### Warehouse Loading DAGs

Several DAGs were implemented to support warehouse operations.

#### daily_crypto_summary

Aggregates historical cryptocurrency market metrics from the operational PostgreSQL database into daily analytical summaries.

Responsibilities include:

- daily metric aggregation
- warehouse-friendly transformation
- historical analytical persistence


#### daily_youtube_sentiment_summary

Aggregates YouTube sentiment metrics by publication date.

This DAG performs:

- sentiment aggregation
- engagement averaging
- daily grouping
- analytical summarisation

Importantly, sentiment is aggregated using the original comment publication timestamp (`published_at`) rather than processing timestamps.

This ensures that analytical reporting reflects the true temporal context of social sentiment activity.


#### load_youtube_sentiment_warehouse

Loads sentiment-related dimensions and fact records into the Neon analytical warehouse.

Responsibilities include:

- loading `dim_channel`
- loading `dim_source`
- loading `dim_sentiment_label`
- populating `fact_youtube_sentiment_daily`


#### load_crypto_fact_table

Loads aggregated cryptocurrency metrics into warehouse fact tables.

Responsibilities include:

- warehouse fact population
- historical metric loading
- analytical persistence


### Environment Management

Airflow services run inside Docker containers and rely heavily on environment variable configuration.

Key configuration areas include:

- PostgreSQL operational database connectivity
- Neon warehouse connectivity
- Airflow authentication
- Docker volume propagation

Environment variables are loaded using `.env` files and propagated into Airflow containers during container initialisation.


### Container Networking Challenges

One significant engineering challenge involved Docker networking and warehouse connectivity.

Initially, Airflow containers attempted to connect to PostgreSQL using:

```text
localhost
```

However, inside Docker containers, `localhost` refers to the container itself rather than the host machine.

This required updating the database host configuration to:

```text
host.docker.internal
```

for local PostgreSQL access.

Additional debugging was required to ensure:

- environment variable propagation
- Airflow container recreation
- Neon warehouse connectivity
- DAG environment consistency

These issues are documented further in the debugging notes section.


### Pipeline Monitoring

Basic monitoring and health-check workflows were implemented to validate streaming and warehouse activity.

Checks currently include:

- table existence validation
- row count verification
- recent data availability
- warehouse loading validation
- DAG execution monitoring

The monitoring layer is intended to expand further as the platform evolves.

Future improvements may include:

- automated alerting
- warehouse freshness checks
- Kafka lag monitoring
- DAG failure notifications
- warehouse anomaly detection


### Why Airflow Was Added

The introduction of Airflow significantly expanded the architecture from a simple streaming pipeline into a more realistic analytics platform.

Airflow enables:

- reproducible analytical workflows
- scheduled warehouse transformations
- operational orchestration
- analytical automation
- separation between streaming and analytical concerns

This orchestration layer more closely reflects real-world production data engineering systems.

## Dashboard Consumption Layer

The final layer of the platform consists of dashboard visualisation and analytical reporting using Looker Studio.

The dashboard layer consumes transformed warehouse views from the Neon analytical warehouse rather than directly querying operational streaming tables.

This separation provides:

- cleaner analytical modelling
- improved dashboard performance
- simplified reporting logic
- reduced coupling between ingestion and reporting layers
- more scalable BI architecture

The dashboard layer was designed to provide both operational market visibility and higher-level analytical insight into cryptocurrency sentiment trends.


### Dashboard Architecture

The dashboard connects directly to PostgreSQL views exposed from the Neon warehouse.

These views provide dashboard-friendly analytical models built on top of the warehouse fact and dimension tables.

Key warehouse views include:

- `vw_crypto_price_daily`
- `vw_youtube_sentiment_daily`
- `vw_daily_sentiment_summary`

Using views rather than raw tables simplifies dashboard construction and isolates BI logic from underlying warehouse schema complexity.

## Event Time Alignment

One important analytical issue emerged during dashboard development.

Initially, sentiment metrics were aggregated using processing timestamps (`processed_at`), which incorrectly concentrated all sentiment activity into the day the pipeline happened to run.

This produced misleading dashboard visualisations and invalid correlation analysis.

The issue was corrected by aggregating sentiment using the original YouTube comment publication timestamp (`published_at`).

This ensured that:

- sentiment reflects when comments were actually written
- cryptocurrency prices align with the correct historical social context
- time-series analysis becomes analytically meaningful

This distinction between processing time and event time became one of the most important design lessons of the project.

## Current Limitations

The dashboard currently reflects a relatively limited historical sentiment collection window.

This limitation is primarily due to local infrastructure constraints:

- the platform runs entirely on a personal laptop
- streaming jobs cannot realistically operate continuously for weeks
- sentiment history therefore remains relatively sparse

Despite these constraints, the underlying architecture is designed to scale naturally to larger continuously running environments.

The current implementation demonstrates the full analytical workflow even with limited data volume.
